# 缩进代码围栏渲染修复 — 设计文档

日期：2026-07-02
状态：待实现

## 1. 问题背景

在 Popup（`md_viewer.py`）查看 Markdown 时，**缩进在列表项内的代码围栏**会丢失换行，多行命令被挤成一行显示。

### 复现来源

`G:\UGit\summarize-knowledge\SKILL.md` 第 46-52 行：

```text
- **若不是 git 仓库** → 自动初始化（...）：
  ```bash
  git init
  git remote add origin <远程地址>
  git fetch origin
  git checkout main --track origin/main
  ```
```

围栏 ` ```bash ` 前有 2 个空格（对齐到列表项 `- ` 的内容列）。用户主观认为是"顶格"，但相对文档而言它是**缩进围栏**。

### 根因（已实测确认）

Python-Markdown 的 `fenced_code` 扩展**不识别缩进在列表内的围栏**。缩进的 ` ``` ` 未被当作代码块，反引号退化成**内联 `<code>` 标记**，产物为：

```html
<code>bash
  git init
  git remote add origin ...</code>
```

内联 `<code>` 在 Qt（QTextBrowser）富文本引擎中会把 `\n` 折叠成空格 → 显示成一行。

### 排除的错误假设

- **不是 CSS `white-space` 问题**：实测顶格围栏渲染出的真实 `<pre>` 块换行完全正常，Qt 对 `<pre>` 的换行保留是正确的。
- **不是 `nl2br` 问题**：`nl2br` 只影响正文单换行，不触碰围栏内部。
- **不是 `_normalize_list_indent` 问题**：实测它对围栏内的行正确跳过，未做改动。

结论：问题只出在 `fenced_code` 对缩进围栏的解析，与刚完成的搜索功能、CSS、既有预处理均无关。

## 2. 方案选择

**采用方案 A：预处理去围栏缩进。**

在 Markdown 转 HTML 之前，扫描内容，把**任何带缩进的代码围栏**（围栏行及其内部所有行）整体左移到顶格，使 `fenced_code` 能正确识别为代码块。围栏内代码本身的**相对缩进予以保留**。

已实测：对 `SKILL.md` 全文应用后，6 个围栏全部正确渲染为 `<pre>` 代码块；Python 函数体的相对缩进（4/8 空格层级）完整保留。

### 未采用的方案

- **方案 B（换 `pymdownx.superfences`）**：需引入 `pymdown-extensions` 新依赖、影响打包链、行为变化面大。放弃。
- **方案 C（规范文档写法）**：治标不治本，其他文件仍会踩坑，不符合查看器"兼容常见 Markdown 写法"的定位。放弃。

## 3. 适用范围（已与用户确认）

**所有缩进围栏都去缩进** —— 只要围栏行前有空白，就左移到顶格，不区分缩进量（1/2/3/4+ 空格均处理）。

副作用及接受理由：列表项内的代码块去缩进后会"脱离"列表，成为独立代码块，可能打断列表的序号缩进视觉连贯性。但当前状态下这类代码块**根本渲染不出正确的列表内代码块**（直接坏成一行），因此"独立但正确的代码块"严格优于"坏掉的内联文本"。用户已确认接受此权衡。

## 4. 技术设计

### 4.1 新增函数

在 `md_viewer.py` 的 `MarkdownViewer` 类中新增静态方法 `_dedent_fenced_blocks(content: str) -> str`，与既有 `_normalize_list_indent` 平级。

### 4.2 算法

逐行扫描，维护"是否在围栏内"状态。使用两个正则：

- 开始行：`^(\s*)(`{3,}|~{3,})(.*)$`
- 闭合行：`^(\s*)(`{3,}|~{3,})\s*$`（闭合行只能有标记 + 空白，不带语言标记或其他内容）

步骤：

1. **匹配围栏开始行**。若前导空白（group 1）非空，即为**缩进围栏开始**。
   - 记录缩进字符串 `indent`、围栏字符 `fence_char`（``` ` ``` 或 `~`）、围栏长度 `fence_len`（反引号/波浪号个数）。
   - 输出去掉 `indent` 前缀后的围栏开始行。
2. **进入围栏内循环**，逐行处理直到闭合：
   - **闭合行判断**：匹配闭合正则，且 `fence_char` 相同、长度 **≥** `fence_len`（遵循 CommonMark：闭合围栏数量须不少于开始围栏）。满足则去掉 `indent` 前缀后输出，结束本围栏。
   - **内容行**：若以 `indent` 开头，则删去 `indent` 前缀（**超出部分＝相对缩进，自动保留**）；否则 `lstrip()` 兜底。
3. **顶格围栏**（group 1 为空）与**非围栏行**：原样输出。

### 4.3 边界处理

- **相对缩进保留**：内容行只删去与开始围栏等长的前缀，代码本身的额外缩进（如 Python 函数体）原样保留。已实测通过。若某内容行缩进**少于**围栏行（畸形对齐），不以 `indent` 开头，则退化为 `lstrip()` 安全兜底——此时相对缩进语义本已无意义，全部拍平不会破坏可读性。
- **Tab 缩进**：正则用 `\s` 匹配前导空白，Tab 与空格同样识别并去除。围栏行与内容行的 Tab 前缀按等长删除逻辑处理。已实测通过。
- **围栏与列表间无空行**：最常见写法是列表文字紧接围栏行、中间无空行（如 `SKILL.md`）。此时围栏仍被正确拍平并渲染为独立代码块。已实测通过。
- **围栏字符与长度区分**：``` ` ``` 与 `~` 独立匹配；长度按"≥ 且同类型"判断闭合。这样嵌套场景（如四反引号 ` ```` ` 包住内层三反引号 ` ``` `）不会把内层误判为闭合。已实测通过。
- **围栏未闭合**（文件结尾无闭合行）：循环遇到文件末尾自然结束，已处理的行照常输出。
- **顶格围栏不动**：group 1 为空时不进入去缩进逻辑，零副作用。

### 4.4 接入点

在 `reload_file()` 中，`_dedent_fenced_blocks` 先执行、`_normalize_list_indent` 后执行、再 `md.convert`：

```python
normalized = self._dedent_fenced_blocks(content)      # 新增：先拍平缩进围栏
normalized = self._normalize_list_indent(normalized)  # 再规范列表缩进
md = markdown.Markdown(extensions=[...])
html_body = md.convert(normalized)
```

**顺序说明（重要）**：必须**先 dedent 再 normalize**。原因：`_normalize_list_indent` 会把"行首恰好 3 空格"改成 4 空格，若先跑它、再跑 dedent，围栏缩进量可能被改动导致后续对不齐。先把围栏拍平到顶格后，`_normalize_list_indent` 的 fence 检测会照常跳过顶格围栏内的行，两步彻底解耦、互不干扰。已实测：对 `SKILL.md` 按此顺序处理，6 个围栏全部正确识别、0 残留内联 `<code>`。

## 5. 影响范围

- **单文件修改**：仅 `md_viewer.py`。新增一个静态方法 + `reload_file` 中一行调用。
- **不改用户源文件**：纯内存预处理，磁盘上的 `.md` 不变。
- **不影响顶格围栏**：现有正常渲染的代码块行为完全不变。
- **不影响搜索功能**：预处理在渲染前，与搜索无交互。
